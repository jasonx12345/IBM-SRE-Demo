THE PROJECT IN BRIEF

Checks whether the warnings IBM Research expected during its test failures actually showed up.

What this is: IBM Research ran tests where it made a system fail on purpose. For each test, IBM listed the warnings that should appear. My report compares that list with the warnings IBM recorded, so you can see which ones showed up and which need a closer look.

Why it matters: If a warning never appears, the people keeping a service running might miss a real outage. This project checks for that gap in IBM's test data.

How it works

  • IBM's public ITBench-Lite data says which warnings should appear in each of 35 tests.
  • I compare that list with IBM's saved warning records. Each expected warning is marked observed (found), not observed (not found), or unknown (the records do not give a clear answer).
  • A second, local lab asks: if we turn off two kinds of warnings at once, would we miss a failure that either warning could have helped us spot? It checks two recorded tests.

Key findings

  • I checked 35 public IBM tests.
  • IBM saved 82 lists of active warnings. The same warning can appear in several lists, so the lab counts each continuous run once: 37 warning runs in all.
  • frontend-proxy is the service being watched. If I turn off both its “requests are slow” and “requests are failing” warnings, six warning runs disappear. In the overload test, that leaves no warning linked to the known failure.
  • If I keep the “requests are failing” warning, that failure still has a warning, and the other test avoids a late warning.

This checks IBM Research's public test data, not alerts from IBM's live services. I am not claiming to have invented alert checking.
