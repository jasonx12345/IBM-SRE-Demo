# IBM alert coverage report

This local demo answers one narrow SRE quality-assurance question: **when an IBM Research ITBench-Lite experiment deliberately injected a fault, did the alert snapshots contain the warnings declared in that experiment's ground truth?** It is a report over a public benchmark, not IBM customer production monitoring, a live integration, or proof of pager delivery.

The source is [IBM Research ITBench-Lite](https://huggingface.co/datasets/ibm-research/ITBench-Lite), pinned to revision `d0916b08ba421ce5e672e9ad68aa947d938dfef0` (Apache-2.0). The importer fetches only the 35 SRE experiments' `ground_truth.yaml` and `alerts/alerts_at_*.json` files. It does not download metrics, traces, logs, or unrelated benchmark material. Each source file has a path, byte count, and SHA-256 hash in `seed/itbench-coverage/manifest.json`. Run `.venv\Scripts\python.exe -m ingest.itbench_coverage --download` to reproduce the checked-in report; run without `--download` to rebuild it from verified local files.

For each ground-truth alert declaration, the importer requires a firing alert with the same alert name and namespace, plus a `service_name` or `pod` label matching the declared group's full regular expression. The first matching snapshot is linked directly to the pinned upstream source. Repeated appearances in later snapshots do not turn one expected alert into multiple successes. Declarations for resource types that cannot be matched safely to these labels, experiments without snapshots, and same-name alerts that lack the resource label are marked **unknown**. Experiments with no declared expected alerts are listed but add nothing to the expected-alert totals.

**Observed** means a matching firing row is present in a published snapshot. **Not observed** means no matching row was found in the published snapshots; it is a prompt to inspect the experiment, not proof that a production monitor failed. **Unknown** means the capture or matching evidence is insufficient. These snapshots do not identify when the fault began, whether a notification was delivered, whether an SRE saw it, or whether a user was affected. The report does not calculate detection latency or recommend changing live alert rules.

The earlier alert-retirement replay remains available at `/retirement` for reference. It answers a different counterfactual question using two experiments. The main report does no speculative removal simulation.
